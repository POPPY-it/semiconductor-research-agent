# 技术博客②：RAG 检索链路实测——BM25 vs 向量 vs 混合，结果和你想的不一样（初稿）

> 系列第二篇。上一篇讲了 Agent 内核；这一篇讲我在"半导体行业研报 Agent"里搭建 RAG 检索链路时
> 的一手实测数据——在 45 篇真实文档上的三路检索对比，以及几个反直觉的结论。

## 背景

研报 Agent 要回答"台积电 2nm 进展如何""NVIDIA 最近披露了什么"这类问题，需要从采集到的行业数据里检索依据。RAG 是标准答案，但"检索"这一步怎么搭，有太多说法。我的做法：**先搭一条最简链路，用真实数据测出基线，再谈优化**。

## 组件选型：全部走轻量路线

| 环节 | 选择 | 理由 |
|---|---|---|
| 分词 | 自研字符 bigram（零依赖） | jieba 在 Python 3.10 上构建失败；ASCII 词整体保留 + 汉字相邻二字组，实测够用 |
| Embedding | fastembed + bge-small-zh-v1.5 | ONNX 推理，CPU 上 9ms/查询，94MB 模型，无需 GPU |
| 向量库 | Chroma | 本地持久化、API 简单，生产可平滑迁移 |
| 稀疏检索 | rank-bm25 | 经典 BM25，纯 Python |
| 融合 | RRF（k=60） | 不依赖分数尺度，直接融合排名 |

## 评测设置

- 语料：45 篇真实采集文档（13 条行业新闻 + 32 条 SEC 财报披露记录），全部来自我数据管道的原始输出
- 查询：5 条中文自然语言问题，人工标注相关文档
- 指标：Recall@5、MRR

## 结果：直觉被推翻

| 方式 | Recall@5 | MRR | 平均延迟 |
|---|---|---|---|
| **BM25-only** | **0.65** | 0.70 | 0.1ms |
| Vector-only | 0.425 | 0.40 | 9.1ms |
| Hybrid-RRF | 0.575 | 0.70 | 4.6ms |

三个值得说的点：

**1. 在这个场景里，BM25 赢了向量检索。** 原因很朴素：文档是"标题+元数据"的短文本，查询用词和文档用词高度重叠（"台积电""NVIDIA"是专有名词），词法匹配天然占优。语义向量的价值要等两个条件出现：文档变长、查询开始口语化（比如"做显卡的那家公司最近财报怎么样"）。

**2. 无脑融合（等权 RRF）反而拉低了召回。** 0.65 和 0.425 平均成 0.575——RRF 对弱信号太宽容。下一步我会做**加权 RRF（BM25:向量 = 0.7:0.3）**，再加一个 bge-reranker 做精排，这才是融合的正确姿势：先召回、再重排，而不是先平均。

**3. 评测集本身就是工程的一部分。** 跑完才发现 "SEMI" 这条查询在语料里零相关文档（Recall 恒 0），这种标注噪声只有亲手跑一遍才能暴露。下一轮我会换成文章正文语料 + 更细的标注。

## 踩坑两则

- **chromadb 拒绝 numpy 类型**：fastembed 返回 `np.float32` 数组，`list(vector)` 得到的还是 numpy 标量，chroma 类型校验直接报错。`.tolist()` 解决。这类"库与库之间的类型契约"问题，调试时间往往比写业务代码还长。
- **模型下载**：HuggingFace 直连超时，`HF_ENDPOINT=https://hf-mirror.com` 走镜像，一秒解决。

## 结论

"BM25 vs 向量"没有标准答案，只有**在你的数据上测出来的答案**。先建基线（哪怕只有 45 篇文档），再谈优化，比我一开始就上重排器、多路召回、query 改写要靠谱得多。
