# 技术博客③：多 Agent 协作与质检链路——一个研报 Agent 的生产化实践（初稿）

> 系列第三篇。前两篇讲了 Agent 内核和 RAG 检索链路，这一篇把两者接起来：
> 研究/数据/质检三个 Agent 如何协作生成一份"可交付"的行业研报，以及我在
> 312 个真实知识分块上的最终检索方案选型。

## 先看检索链路的最终答卷

上一篇的结论是"短文档上 BM25 赢"。这一轮我把语料升级成了**长文档**：
从 SEC EDGAR 抓取了 29 篇半导体公司财报全文（10-K/10-Q/6-K，Workiva 生成的
HTML，还踩了 EDGAR 包装格式的坑——正文 HTML 被转义塞在 `<TEXT>` 段里，
必须解出再解析），加上新闻正文，共 34 篇文章、切分后 312 个分块。

评测结果（Recall@5 / MRR / 每查询延迟，全部预热后计时）：

| 方式 | Recall@5 | MRR | 延迟 |
|---|---|---|---|
| BM25-only | 0.355 | 0.643 | 0.4ms |
| Vector-only | 0.298 | 0.500 | 4.6ms |
| RRF 等权 | 0.337 | 0.679 | 4.8ms |
| RRF 加权(0.7/0.3) | 0.337 | 0.619 | 5.2ms |
| **加权 RRF + bge-reranker** | **0.391** | 0.643 | 5632ms |

三个结论：

1. **长文档上向量和 BM25 差距缩小了**，但 BM25 依旧便宜好用——0.4ms 的基线别轻易丢。
2. **重排器显著提升召回（+16%）**，但 CPU 上 5.6 秒/查询。所以我的产品策略是：
   **交互式检索走加权 RRF（毫秒级），研报生成这种离线任务才开重排器**——延迟预算由场景决定。
3. 评测工程本身要严谨：我第一次跑出来的"延迟"把一次性索引成本算进去了，预热后 BM25 从
   "1722ms" 变成真实的 0.4ms。**不预热的评测数字和造谣没区别。**

## 多 Agent 编排：研究 → 质检 → 修订

一个能直接交给用户的研报，光有检索不够，还需要"写的人"和"检查的人"。我的编排：

```
研究 Agent（CodeAgent + 检索工具 + 财报工具）
    │  输出：带来源引用的 Markdown 报告
    ▼
质检 Agent（CodeAgent + 同样的工具）
    │  输出：JSON {"passed": bool, "issues": [...]}
    ▼
passed? ──否──▶ 把 issues 反馈给研究 Agent（reset=False 保留上下文）→ 修订 → 再质检（最多 2 轮）
    │是
    ▼
落盘 + 交付
```

几个设计点：

- **两个 Agent 用同一套工具，指令不同**：研究 Agent 的 system prompt 是"只能基于检索结果撰写、每个数字必须注明来源"；质检 Agent 的是"校验每个论断能否被检索结果支持，只输出 JSON"。同一个 CodeAgent 内核，靠 prompt 分化角色。
- **质检失败不直接报错**：把质检 JSON 里的 issues 原文喂回研究 Agent，让它带着上下文修订——这比"整轮重跑"省 token，而且修订结果通常明显变好。
- **质检输出用正则兜底解析**：模型偶尔会在 JSON 外包一层解释文字，`re.search(r"\{.*\}")` 再 json.loads，解析失败按"不通过"处理，保证流程不崩。

## 演示：跑一份真实的周报

选题："本周半导体行业动态周报（聚焦 NVIDIA/台积电/Intel/ASML）"。研究 Agent 检索了
312 个知识分块，产出一份 87 行的 Markdown 周报——四家公司分节、财务数据透视表、
每条数据带 SEC 原文链接、末尾有风险提示和免责声明。节选：

> 根据台积电向 SEC 提交的月营收报告，2026 年 7 月合并营收约为新台币 4675.8 亿元，
> 同比增长 44.7%……（[SEC 链接](https://www.sec.gov/Archives/edgar/data/1046179/000104617926000471/tsm-revenue20260810.htm)）

质检 Agent 的判定很有意思——它打了 **passed: false**，理由是：

> "ASML 2026 Q2 总净销售额 93 亿欧元、全年指引 430-450 亿欧元等数据未能在检索结果中找到对应支持。"

但报告里的这些数字**都带着真实 SEC 链接**。也就是说：数字很可能是对的（来源链接都在），
只是质检 Agent 用不同关键词检索时没命中相同分块——**质检不是真伪的法庭，而是"可验证性"
的门槛**。对生产系统来说，这个门槛本身就是价值：凡是被标记"不可验证"的数字，
要么被修订轮降级表述，要么留给用户人工复核，这就是幻觉治理的务实做法。

另一个成本发现：修订循环用 `reset=False` 保留上下文，第二轮输入 token 累计到 52 万——
**上下文是 Agent 流水线最贵的资源**。所以修订轮数必须设上限（我设 2 轮），并且把
完整报告回填上下文的做法要优化成"只回填问题段落"（这是我下一轮的优化点）。

## 对面试有用的三个话题

1. 延迟预算怎么分场景（交互毫秒级 / 离线可秒级）——这是"工程判断"类问题的好素材
2. 评测要预热、指标要贴真实数据——别拿没预热过的数字写博客
3. 多 Agent 不是越多越好：两个 Agent + 一个修订循环，比五个 Agent 开会可靠
