## 1. 执行摘要

### 1.1 总体判断

这是一个**方向正确、工程闭环明显强于普通 Demo，但距离可公开商用的企业级产品仍有显著距离**的垂直研究 Agent。

项目最有价值的地方，不是“调用大模型生成一篇研报”，而是已经形成了相对完整的链路：

- 多源采集与本地知识库；
- 混合检索、重排和实体共现图；
- 规划、分节研究、事实质检、局部修订；
- 报告、轨迹和评测落盘；
- FastAPI、SSE、任务队列、前端工作台；
- 引用纪律、合规模板、预算熔断和降级策略。

这使项目具备较强的**求职作品、技术验证和小团队内部工具**价值。

但从项目管理和商业交付角度看，当前最大的矛盾是：

> **产品对外呈现接近“Enterprise”，实际安全边界、质量指标、数据规模、可用性和运维能力仍主要适用于单用户自托管或演示环境。**

因此，当前不应继续横向堆叠更多热门能力，而应优先完成四件事：

1. **收窄并明确目标场景**：先做好半导体公开信息研究，不要同时承担行业研报、研投、学术和医学四条主线；
2. **把质量门槛从提示词约束升级为确定性门禁**：尤其是数字引用、来源可信度和质检一致性；
3. **封闭高风险执行入口**：前端内置 Token、任意 MCP 命令执行、无限制文件上传等；
4. **建立可持续交付证据**：先修复评测重复运行入口，再统一口径重跑评测、连续运行、真实任务验收、备份恢复和安全基线。

## 3. 值得肯定的想法和方向

### 3.1 定位不是通用聊天机器人，而是“带证据的研究生产线”

README 的一句话定位清楚：选题进入后，通过公开财报和论文检索，产出带引用报告，并用评测集验证引用和工具调用。这个方向比“万能 Agent”更容易形成可验证价值。

值得坚持的产品原则：

- 输出必须能追溯；
- 检索和工具调用可回放；
- 质量问题必须被显性表达；
- 不应把模型自信程度当作事实正确性。

### 3.2 “研究者 + 质检者 + 局部修订”比单次生成更合理

`agent/orchestrator.py` 已经形成：规划 → 分节研究 → 质检 → 最多两轮局部修订。这一结构符合研究型任务的真实工作流，也便于后续引入确定性检查和人工审批。

尤其值得肯定：

- 质检失败不静默；
- 支持 `caveat` 和 `reject` 两种交付策略；
- 修订要求只处理问题段落，避免全文重写导致已正确内容漂移；
- 轨迹保存规划、步骤、质检、预算、耗时和引用指标。

### 3.3 工具治理意识强于多数同类项目

`agent/tools.py` 对核心工具设置了必填参数、范围、超时、重试、降级与故障注入；MCP 工具也有限制输出长度、枚举归一化和选择白名单。这表明项目作者已经从“工具能调用”转向“工具可治理”。不过当前治理并未完全统一：PubMed 仍走独立裸请求，动态 MCP 工具也不属于静态 `TOOL_META` 范围，因此更准确的评价是“治理框架方向正确、核心路径部分落地”。

这是很好的工程方向，应继续深化为：工具权限、来源信誉、调用预算、幂等性、审计和隔离。

### 3.4 评测没有只报喜，能够暴露方法论问题

项目公开记录了真实语料 Recall 偏低、judge 上下文不足、无引用数字率偏高、必用工具漏调用和预算熔断。这种诚实比虚假的 95% 准确率更有长期价值。

特别是 `eval/metrics.md` 中明确给出：

- 任务成功率 0.652；
- 平均无引用数字率 0.577；
- 平均 88.1 步、145.8 次工具调用；
- 24 条任务中 1 条预算熔断。

这些结果虽然不好看，但为后续治理提供了真实基线。

### 3.5 对合规边界已有初步产品化处理

基本面分析禁止目标价和买卖建议，医学综述禁止诊疗建议，并自动追加免责声明。虽然免责声明不能替代实质性治理，但把边界写进模板、测试和交付策略，是正确起点。

### 3.6 工程闭环较完整

项目已经包含：

- 单元/集成测试和 CI；
- Docker 多阶段构建；
- 数据与报告持久化；
- SSE 任务进度；
- 请求 ID、限流、健康检查和基础指标；
- 主备模型、预算熔断和外部数据源降级。

作为个人或小团队项目，完整度是明显优势。

## 4. 核心缺点与风险

严重度定义：

- **P0 / 严重**：可能导致远程执行、密钥泄漏、错误高可信交付或无法公开部署；
- **P1 / 高**：明显影响产品价值、可靠性、成本或企业验收；
- **P2 / 中**：影响维护效率、体验或扩展能力；
- **P3 / 低**：规范性和长期优化事项。

### 4.1 产品定位和范围过宽（P1）

当前同时覆盖：半导体日报/周报/深度研报、投资基本面、学术综述、医学综述、问答、MCP 管理、长期记忆、知识图谱。

问题在于：

1. “半导体研究 Agent”与“医学综述”目标用户、数据源、风险边界完全不同；
2. 每增加一种模板，都需要独立黄金集、来源规则、事实校验和合规验收；
3. 数据只有约百篇量级，却呈现多个专业领域，容易形成“功能很多、每项都不深”；
4. 产品故事从垂直研究工具变成技术能力陈列。

**建议**：主版本只保留半导体行业研究和上市公司基本面两类；学术能力作为“半导体技术论文调研”；医学能力迁出主产品或明确标记为实验插件。

### 4.2 “Enterprise”品牌承诺超过当前能力边界（P1）

前端展示 `Enterprise v0.3.0`，但当前是共享 Token、单用户 Cookie、SQLite、进程内事件总线/指标/限流，默认线程池队列。README 虽然诚实说明单用户，但 UI 品牌会产生更高预期。

企业通常至少要求：

- 多用户身份与组织隔离；
- 角色权限和资源授权；
- 审计日志；
- 任务持久化与可靠恢复；
- 密钥托管；
- 备份恢复；
- 数据保留与删除策略；
- 安全更新和漏洞响应；
- 可衡量 SLA/SLO。

**建议**：在完成上述能力前，产品级别命名改为“Research Workbench / Engineering Preview”，或在 UI 明示“单用户自托管版”。

### 4.3 高可信定位与真实质量指标冲突（P0/P1）

目前最需要正视的数据是：历史 Harness 的平均无引用数字率为 **0.577**，且部分质检通过任务无引用率达到 1.0。这说明：

- LLM 质检与确定性指标不一致；提示词中的“实时搜索最多调用 2 次”“每节最多 1 次”也没有代码计数器强制执行；
- “passed=true”不能证明数字已被支持；
- 提示词中的“数字必须带来源”并未成为可靠门禁；
- 当前 `caveat` 默认策略可能让低质量报告继续交付。

这是产品核心价值风险，而不是普通优化项。

**建议**：

1. 把数字-引用检测改成服务端确定性门禁，失败时禁止标记通过；
2. 为每个重要 claim 建立 `claim → source_id → source_span → retrieved_at` 结构；
3. 将来源分为官方披露、论文、主流媒体、聚合站、用户上传，并设置可信度；
4. 对财务数字做单位、币种、期间、GAAP/Non-GAAP、同比/环比一致性校验；
5. 对交付设硬阈值，例如关键数字支持率 100%、普通数字支持率 ≥95%；
6. 默认使用 `reject`，只有内部预览环境允许 `caveat`。

### 4.4 评测集规模和口径不足以支撑结论（P1）

mini 黄金集只有 8 条，Agent 任务集 24 条，而且文档明确承认：

- 真实语料标注过粗；
- judge 上下文与实际来源不一致；
- 24 条结果来自不同代码阶段合并，口径不统一；
- 新规划和数字纪律尚未全量重跑验证。

因此当前指标适合开发调试，不适合作为产品质量证明。

**建议**：

- 建立 100~300 条分层任务集；
- 按公司、主题、报告类型、难度、时效性、来源类型分层；
- 精确标注到文档和段落；
- 固定模型、温度、数据快照和依赖版本；
- 每个版本完整重跑，禁止跨版本拼接主指标；
- 先修复评测命令的重复执行能力：`build_retriever` 默认不 reset，持久化 Chroma 集合使用 `collection.add()`；当前 `run_harness.py` 也未显式 reset。固定 doc_id 已存在时会触发重复 ID 错误，因此 README/P7 所述命令不能作为可靠的重复运行入口。评测应使用隔离临时索引、显式重建或幂等 upsert；
- 所有对外引用率数字必须能追溯到评测产物，未发现原始结果支撑的历史口径不得继续作为宣传指标；
- 增加人工专家双人复核与一致性统计；
- 将质量、成本、时延做成统一发布门禁。

### 4.5 Harness 的“成功”定义没有验证任务事实（P0/P1）

`agent/harness.py` 当前把任务成功定义为：质检模型通过，或无引用数字率恰好为 0；`eval/tasks.json` 中预先设计的 facts/checkpoints 并未进入成功判定。换言之，任务可能文字完整、链接很多且被同一模型判定通过，但仍没有回答黄金事实。

这会导致“任务成功率 0.652”主要衡量自评与引用形式，而非事实正确性。已有产物抽查还发现部分报告混入模型过程性文本，但仍曾被判通过，说明仅靠同模型 QA 存在假阳性风险。

**建议**：成功定义至少同时满足：任务 checkpoint 命中、关键 claim 有原文证据、确定性数字规则通过、独立 judge/人工抽检通过、输出不含过程性泄露；失败应区分事实错误、引用错误、格式污染、工具遗漏和预算错误。

### 4.6 成本和执行效率偏低（P1）

历史基线显示平均每篇：

- 约 313.6 秒；
- 88.1 个步骤；
- 145.8 次工具调用；
- 14.43 个错误；
- 约 189 万预算字符。

虽然单篇成本估算低于 3 元，但步骤和调用数量反映了明显的上下文膨胀与 Agent 失控风险。增加数据规模和实时检索后，成本可能非线性增长。主模型切换到 fallback 时会新建一套独立 `BudgetedModel`，当前预算不是主备模型共享总额度，理论上可再次消耗完整预算；同时预算依据字符量而非服务商实际 token 用量，不能作为精确成本上限。

**建议**：

1. 将开放式 Agent 缩为可控工作流：规划器只产结构，检索器批量召回，写作者只消费结构化证据包；
2. 避免每节重建过长上下文；
3. 增加查询去重、结果缓存、来源摘要缓存；
4. 先用规则筛选和轻模型，再让强模型处理高价值步骤；
5. 对每阶段设置独立预算、超时和最大调用数；
6. 记录实际 API token 与费用，不只用字符估算。

### 4.7 前端内置默认 Token，且工作区存在可复用认证材料（P0，需按安全事件处理）

`frontend/src/api.ts` 将 `VITE_API_TOKEN` 打入浏览器构建产物，并设置默认值 `dev-token-2026`；`spikes/loadtest.py` 也写有同一值。Vite 环境变量会进入客户端 JavaScript，无法作为秘密保存。

工作区及 Git 历史还存在 `spikes/cookies.txt`。只读安全核查通过 HMAC-SHA256 复算确认：历史 Cookie 使用的签名密钥与代码中的弱开发 Token 相同。由于 Cookie 只校验签名与过期时间，掌握该值的人可以自行构造未来过期时间的有效 Cookie。无论远端仓库当前是否公开，都不应继续信任现有开发凭据和历史 Cookie。

构建产物扫描也确认默认 Token 已进入 `frontend/dist`。Dockerfile 构建前端时没有提供用户交互式登录机制或安全的凭据注入流程；如果后端改为不同的强随机 Token，现有前端默认登录会失败，而让前后端继续共用公开弱值则等于放弃认证。这不是简单的环境配置问题，而是认证流程设计缺陷。

即使后端再换 Cookie，首次登录请求仍由浏览器提交该 Token；任何访问页面的人都能从构建产物或网络请求中获得它。共享 Token 也无法区分用户和审计责任。

**立即处置建议**：

1. 轮换 API Token、Cookie Secret、LLM/MCP 等外部服务凭据；
2. 删除和吊销现存 Cookie，清理仓库历史与构建产物中的认证材料；
3. 核验远端仓库可见性、访问日志和外部密钥调用记录；
4. 不在前端构建中嵌入任何服务器秘密；
5. `COOKIE_SECRET` 必须独立生成，禁止回落到 API Token 或开发默认值；
6. 自托管单用户版使用首次启动引导或服务端登录页，由用户输入凭据；
7. 团队版接入 OIDC/OAuth2；
8. Cookie 设置 `Secure`，生产环境强制 HTTPS，并支持服务端吊销；
9. 对修改类请求增加 CSRF 防护；
10. 支持 Token 轮换、失败锁定与审计。

### 4.8 MCP Server 管理允许执行任意命令（P0）

`POST /api/v1/mcp/servers` 接受任意 `command + args`，随后服务端通过 stdio 子进程执行。代码注释已经承认该边界。

这意味着：一旦共享认证凭据泄漏，攻击者可能获得服务器命令执行能力。即使是内部部署，也会形成供应链、误操作和提示注入联动风险。

**建议**：

1. 生产环境彻底关闭网页新增任意命令；
2. 只允许管理员从服务端配置的已签名/已审核清单启用工具；
3. MCP 工具在独立低权限容器或沙箱运行；当前 stdio MCP 使用 `os.environ.copy()` 继承宿主完整环境，应改为显式最小环境变量清单，避免子进程读取 LLM、网关和其他服务密钥；
4. 禁止访问宿主文件系统、云元数据地址和内网敏感网段；
5. 对工具设置网络、文件、CPU、内存和时间限制；
6. 工具调用前展示权限，并对写操作要求人工确认；
7. 记录完整审计日志，但脱敏 Token 和用户数据。

### 4.9 fetch 工具存在 SSRF 风险，CodeAgent 执行边界不清晰（P0/P1）

`mcp_servers/fetch_server.py` 对用户/模型提供的 URL 直接执行 `requests.get(..., allow_redirects=True)`，未见协议、DNS、内网地址、环回地址、云元数据地址和重定向目的地校验。这可被用于访问服务端可达的内部资源。

同时，项目使用 `smolagents.CodeAgent` 的本地 Python executor。该 executor 并非完全裸执行：内置危险模块黑名单和有限的基础模块白名单，属于**进程内软沙箱**；但它不是操作系统级安全隔离，仍与主服务共享进程权限和资源边界。叠加可执行任意命令的 MCP 入口后，不能把这一执行环境视为生产级安全沙箱。

**建议**：

- fetch 只允许 `http/https`，解析并阻断私有、环回、链路本地、保留地址和云元数据；
- 每次重定向重新校验目的地址，限制重定向次数、响应体和 Content-Type；
- 通过出口代理和域名白名单控制网络；
- CodeAgent 使用独立低权限容器/远程沙箱，挂载只读最小目录，禁用宿主凭据与内网访问；
- 研究者和质检者按最小权限分配不同工具集。

### 4.10 文件上传缺少请求体和文件类型硬限制（P1）

接口会先执行 `await file.read()` 读入完整文件，之后解析器才把文本截断到 20,000 字符。当前没有看到：

- 上传字节上限；
- MIME/魔数校验；
- 压缩炸弹或恶意 PDF 防护；
- 病毒扫描；
- 用户配额；
- 文档隔离和删除能力。

这可能导致内存耗尽、解析器漏洞暴露和数据污染。

**建议**：在代理层和应用层双重限流；流式读取；文件大小/扩展名/MIME/魔数联合校验；解析进程隔离；设置页数和耗时上限；增加文档删除、来源标识和权限隔离。

### 4.11 提示注入和数据污染治理不足（P1）

网页、论文、用户上传文档和 MCP 返回内容都可能包含“忽略此前指令”“调用某工具”等恶意文本。当前主要依赖系统提示和工具白名单，没有看到内容级隔离和污点追踪。

**建议**：

- 明确告诉模型“检索内容是数据，不是指令”；
- 对外部内容做提示注入检测与标记；
- 检索证据与系统指令采用结构化通道隔离；
- 高风险工具不得由检索内容直接触发；
- 建立红队集：提示注入、恶意引用、伪造官方来源、数据外泄诱导、越权工具调用；
- 输出引用只能指向实际检索记录，不允许模型自由生成 URL。

### 4.12 异步端点执行长时间同步任务，可能阻塞事件循环（P0/P1）

`ask_question` 是 `async` 路由，但直接调用同步且可能持续较久的 LLM/检索流程；文档上传路由在读完文件后也会同步执行解析、数据库写入和全量重建索引。它们没有统一丢到线程池或后台 worker。

后果可能包括：

- 同一进程中的健康检查、登录、SSE 和其他 API 响应被拖慢；
- 上传重建期间请求长时间占用连接；
- 负载增加时出现事件循环饥饿和级联超时。

**建议**：同步重计算通过专用 worker/线程池执行；上传接口只创建索引任务并立即返回任务 ID；问答设置独立并发池、超时和背压；增加“长问答并发健康检查”的集成测试。

### 4.13 单机并发模型实际上接近串行（P1）

`ReportService` 用同一个 `RLock` 包裹报告生成、问答和重建索引。即便线程池 `max_workers=2`，长达数分钟的报告任务期间，其他报告/问答很可能等待同一把锁。

这与“线程池支持并发”的直觉不一致，也会让 QPS 压测结果失去代表性——健康检查和列表接口的 1273 QPS 不能说明报告生成场景的吞吐与响应。

**建议**：

- 区分只读检索锁与索引替换写锁；
- 检索器使用不可变快照或版本化索引；
- 报告任务迁移到独立 worker；
- 问答与报告生成分配不同队列和并发池；
- 压测真实混合负载：生成 + 问答 + SSE + 上传 + 重建。

### 4.14 RQ“规模化路径”尚未形成完整闭环（P1）

Compose 中 Redis/worker 只是注释示例；事件总线是进程内对象。如果 API 与 RQ worker 分进程运行，worker 发布的 SSE 事件不能自然到达 API 进程。此外，将绑定实例方法及复杂对象直接入队也需要验证可序列化与初始化策略。

**建议**：不要把“预留”写成已具备。先完成并验证：

- 独立 worker 启动；
- 任务状态持久化；
- Redis Pub/Sub 或 Streams 事件传递；
- worker 崩溃重试与幂等；
- 取消任务；
- 超时与死信；
- 多进程端到端测试。

### 4.15 可观测性指标不够标准和完整（P2）

当前是自定义进程内计数器，输出类似 Prometheus 文本，但：

- 多进程无法聚合；
- 重启后清零；
- 限流 `_buckets` 只过滤时间戳而不回收过期客户端 key，长期面对大量不同 IP 时字典会持续增长；
- label 生成方式不标准；
- 缺少直方图、分位数、队列等待、模型 token、工具耗时、缓存命中等；
- `/api/metrics` 无鉴权，可能暴露系统信息。

**建议**：使用标准 Prometheus client 或 OpenTelemetry，统一 trace_id/run_id/request_id，建立仪表盘和告警。重点监控：任务成功率、质检通过率、关键数字支持率、各工具错误率、LLM 成本、P50/P95、队列积压和索引版本。

### 4.16 文档和实现存在口径漂移（P2）

典型表现：

- README 写“43 个测试”，本次实际为 77 个；
- `.env.example` 默认预算 400 万，代码默认 600 万；
- 市场分析仍把 MCP、GraphRAG、记忆标为缺失，但 README 表示已实现；
- PLAN 同时保留大量未勾选任务和已完成说明；
- 部署文档中的生成耗时与后续成本报告不完全一致。

**建议**：

- 建立单一事实源：版本状态、指标和功能矩阵由脚本生成；
- 将 PLAN 归档为历史设计，不继续作为当前路线图；
- 每次发布自动更新测试数、版本号和评测摘要；
- 文档标记“当前 / 计划 / 实验 / 已弃用”。

### 4.17 认证、数据暴露和本地秘密治理仍不完整（P1/P2）

除前端 Token 和 Cookie 可伪造问题外，认证治理还有以下缺口：

- 登录接口使用普通字符串比较 Token，而非恒定时间比较；
- Cookie 没有设置 `Secure`，也没有服务端会话记录或吊销机制，logout 只删除当前浏览器 Cookie；更严重的是，Cookie 验证路径没有要求 `auth_enabled()` 为真：当 API Token 未配置时，签名密钥会回落到公开默认值 `dev-insecure-secret`，理论上可直接伪造 Cookie 通过鉴权；
- `/api/health`、`/api/metrics` 和 `/charts` 未鉴权，分别可能暴露模型/队列信息、运行指标和报告图表；
- 系统为单一共享 Token，所有会话、记忆、文档和报告没有对象级授权；若被误用为多用户服务，将形成直接越权访问；
- Windows ACL 核查显示工作区 `.env` 对普通已认证本地用户权限过宽，应仅允许运行账户和管理员访问；
- Agent 轨迹、报告、SQLite 数据和运行日志明文保存，且缺少统一保留期限、脱敏、导出和删除策略。

**建议**：生产环境强制 HTTPS/Secure Cookie；使用短期服务端会话和吊销列表；收紧健康、指标和图表访问；明确单用户部署边界；调整 `.env` ACL；建立数据分类、保留、清除和日志脱敏制度。

### 4.18 项目治理与许可证不完整（P1/P2）

工作区根目录未发现项目自身 LICENSE、SECURITY、CONTRIBUTING、CHANGELOG。README 说明复用 Apache-2.0 的 smolagents，但项目自身许可和第三方通知不明确。

这会影响开源传播、企业使用和贡献协作。

**建议**：明确项目许可证；保留第三方版权与 NOTICE；增加安全披露渠道、贡献指南、变更日志和版本发布规范；对 Python/Node/Docker 依赖生成 SBOM 并进行许可证扫描。

### 4.19 前端工程门槛偏低（P2）

`tsconfig.json` 设置 `strict: false`，API 中使用多处 `any`；package scripts 没有 lint、typecheck、unit test、e2e test。独立执行 `tsc --noEmit` 已发现一处真实错误：`SessionDetail.tsx:229` 在 ES2020 lib 下使用 `events.at(-1)`。当前 CI 只做 Vite build，而 Vite 默认不承担完整 TypeScript 类型检查，因此该问题没有成为流水线门禁。前端导航和状态文案也存在“静态宣称就绪”的问题，例如固定显示知识引擎就绪，而非基于真实健康状态。

**建议**：

- 启用严格类型并消除关键 `any`；
- CI 增加 typecheck、lint、组件测试和 Playwright 核心流程；
- 状态徽章从真实 API 获取；
- 显示数据更新时间、索引版本、任务队列等待和来源覆盖；
- 对长任务提供取消、断线恢复、失败原因、成本预估和阶段耗时。

### 4.20 服务边界、限流和生命周期存在工程隐患（P1/P2）

除长任务阻塞和全局锁外，还发现以下需要纳入近期整改的细节：

- `RateLimitMiddleware` 的路径判断使用 `request.url.path in prefix`，匹配方向不自然，动态子路径也缺少可靠规则，容易出现漏限流；
- 直接信任 `X-Forwarded-For`，若没有受信任反向代理清洗，客户端可伪造 IP 绕过进程内限流；
- `recover_stale()` 在应用构造/模块导入阶段执行，而不是 FastAPI lifespan，测试导入和多 worker 启动时可能产生意外状态变更；
- SSE 生成器没有显式检查客户端断开，服务端可能继续保留无效订阅；
- `RQQueue.status()` 返回 RQ 原生状态，与抽象接口约定的状态名称不完全一致，且缺少该路径的端到端测试；
- 项目通过 `sys.path` 修改解决包导入，且缺少根 `pyproject.toml`，长期会增加跨层依赖和打包复杂度。

**建议**：修正并测试限流路由规则；只信任受控代理转发头；将启动恢复迁入 lifespan；增加 SSE 断开检测；统一队列状态契约；用标准 Python 包配置和依赖注入替代 `sys.path` hack。

### 4.21 测试会污染正式报告产物目录（P2）

`tests/test_planner.py::test_generate_injects_plan_into_researcher_task` 虽把轨迹、记忆和向量目录指向 `tmp_path`，但调用 `pipeline.generate()` 时没有传入临时 `output_dir`，因此会按默认路径向 `reports/output` 写入 `# 报告 / 正文` 占位文件。

产物目录抽查显示，大量报告是测试生成的空壳，这会：

- 污染演示和人工质量抽查；
- 让报告数量、通过率和历史记录失真；
- 容易被误判为真实生成失败；
- 增加仓储和保留治理难度。

**建议**：所有测试输出强制使用 `tmp_path`；测试和生产报告使用不同根目录及明确 metadata；清理历史占位产物前先生成清单并确认；CI 增加“测试不得写工作区正式产物目录”的断言。

### 4.22 容器和供应链仍需加固（P2）

当前 Dockerfile 的积极点是多阶段构建和固定 Python 依赖版本；不足包括：

- Node 依赖使用 `npm install`，不是基于 lockfile 的 `npm ci`；
- 生产依赖通过镜像源安装，需考虑可用性、审计和来源策略；
- 容器默认 root；
- 基础镜像使用可漂移 tag；
- 数据、模型、源码一起复制可能增大镜像；`COPY data ./data` 还可能把本地 `articles.db`、`app.db`、`memory.db`、向量索引和测试数据快照打进镜像，部署时再被 volume 覆盖，既有数据泄露风险也容易造成环境认知混乱；
- 未见镜像扫描、SBOM、签名、只读文件系统和 capability 收缩。

**建议**：锁定镜像 digest；非 root 运行；`npm ci`；分离模型/运行数据；CI 增加依赖、镜像、密钥和许可证扫描。

## 5. 多维度详细评审

### 5.1 产品与用户价值

#### 当前优势

- “公开信息研究 + 可追溯引用”价值明确；
- 研报生成与问答两个入口符合研究人员工作流；
- 历史任务、报告阅读、来源面板和过程展示有产品雏形；
- 半导体垂直领域便于积累术语、公司、供应链和指标体系。

#### 主要不足

- 缺少清晰的首要用户画像：学生、个人投资者、行业分析师还是企业研究团队；
- 缺少用户任务优先级和使用频率数据；
- 输出仍偏“生成长文”，没有深入研究工作流中的对比表、数据导出、证据批注、协作审核和版本差异；
- 没有定义“用户为什么不用通用 Deep Research 或金融终端”。

#### 建议产品主张

建议聚焦为：

> **面向半导体研究人员的公开信息证据工作台：把 SEC 披露、公司公告、行业新闻和技术论文整理成可审计的证据包与研究初稿。**

“证据包”应成为比“自动研报”更核心的交付物，因为它更可控、更容易建立信任，也更适合人机协作。

### 5.2 项目管理与交付

#### 当前优势

- 有 8 周计划、里程碑、风险和复盘材料；
- 能根据第三方意见整改；
- 有成本、压测、评测和竞品记录；
- 能明确哪些是复用、哪些是自研。

#### 主要不足

- 计划以技术模块为主，缺少用户验收标准；
- 完成状态多以“代码存在/测试通过”为准，不等于“用户价值达成”；
- 路线图易受热点驱动：MCP、GraphRAG、记忆、多模态都被列入；
- 缺少版本发布、风险责任人和退出标准。

#### 推荐管理方式

采用“目标—指标—里程碑—退出标准”四层：

- 目标：研究人员 10 分钟内得到可核验初稿；
- 指标：关键 claim 支持率、人工节省时间、有效来源占比、返工率；
- 里程碑：证据模型、质量门禁、连续运行、专家验收；
- 退出标准：指标不达标则不继续扩展新能力。

### 5.3 架构与可维护性

#### 当前优势

- `agent`、`backend`、`data`、`frontend`、`eval`、`tests` 分层直观；
- 外部工具治理集中；
- 服务层通过 factory 延迟加载重型索引；
- 轨迹和评测具备一定可回放性。

#### 主要不足

- `backend/app/main.py` 超过 460 行，包含认证、会话、问答、记忆、MCP、上传、静态资源等多类职责；
- `agent/orchestrator.py` 同时承担规划、Agent 创建、容错、生成、质检、修订、落盘、问答和记忆；
- 配置以 class 属性在 import 时读取，不利于测试隔离和动态配置；
- 多处吞掉异常，虽然保障主流程，但削弱问题可观测性；
- 服务层和 Agent 层互相引用配置，边界不够干净。

#### 建议目标架构

- API 路由按 auth/report/qa/document/mcp/admin 拆分；
- 领域层定义 Task、Evidence、Claim、Report、Verdict；
- 工作流层只编排阶段，不直接处理持久化细节；
- 工具执行层独立权限和沙箱；
- 评测复用与生产完全相同的证据对象和工作流；
- 配置采用可注入 Settings 实例。

### 5.4 数据、检索与知识治理

#### 当前优势

- BM25 + 向量 + RRF + reranker 是合理组合；
- 有真实 SEC/arXiv/PubMed/RSS 数据；
- 能记录来源 URL；
- 有 mini 基线与真实数据反思。

#### 主要不足

- 数据量和覆盖面不足，且缺少来源 freshness、失败率、重复率、字段完整率等质量指标；`loader.py` 还使用固定 `limit=1000`，随着数据增长会形成隐性截断；
- 数据源名称与可用内容不完全等价：只读数据库核查显示 Google News 条目虽有 30 篇，但正文为空；新浪科技当前为 0 条。因而“接入新闻源”不能直接推导为“拥有可检索新闻正文”；
- PubMed 实时检索在 `data/collectors/pubmed.py` 内直接使用 `requests.get`，没有复用 `agent/tools.py` 的统一 `external_get` 治理，导致超时、重试、故障注入和降级策略口径分裂；
- Google News 采集器把代理硬编码为 `127.0.0.1:10808`，离开当前开发机后默认不可用，应改为可选环境配置并提供直连/代理降级；
- SEC 查询工具返回标题、日期和 URL，不直接返回结构化财务事实；
- 实体共现图不等于知识图谱，不能支撑严谨关系推理；
- 用户上传内容可能污染全局知识库；
- URL 本身不是稳定证据，网页内容可能变化。

#### 建议

- 存储来源快照、哈希、抓取时间、解析版本和许可信息；
- SEC 使用 XBRL/Company Facts 建立结构化财务指标层；
- 每条证据保留原文 span 和定位信息；
- 用户文档进入独立空间，不默认混入公共索引；
- 增加数据质量看板和采集 SLA。

### 5.5 安全、隐私与合规

当前仅适用于受信任的单用户自托管环境。若要公开部署，应先完成：

- 身份与权限体系；
- MCP 执行隔离；
- 上传防护；
- CSRF/HTTPS/Secure Cookie；
- 秘密管理和轮换；
- 数据删除、导出、保留期限；
- 审计日志；
- 提示注入红队；
- 依赖和镜像供应链治理；
- 投研和医学输出的人审边界。

### 5.6 测试与质量保障

#### 当前优势

- 77 个 pytest 全绿；
- 覆盖工具治理、规划、服务层和企业能力；
- mini 检索评测进入 CI；
- 有历史 Harness 结果。

#### 主要不足

- 前端无自动化测试；
- CI 没有 lint/typecheck/安全扫描；
- 缺少真实外部 API 合同测试与录制回放；
- 缺少并发、崩溃恢复、RQ 多进程和长期稳定性测试；
- LLM 非确定性测试缺少重复运行和置信区间；
- 质量测试没有形成阻断发布的门禁。

#### 建议测试金字塔

1. 规则与领域单元测试；
2. 检索、证据和引用契约测试；
3. 外部 API 录制回放；
4. Agent 小样本每日回归；
5. 全量评测按版本/周运行；
6. 安全红队与故障注入；
7. 前端 E2E；
8. 连续 7~30 天稳定性运行。

## 6. 建议的分阶段改造路线

### 阶段 A：立即止血（1~2 周）

目标：消除不能公开部署的高风险项，统一项目事实口径。

| 编号 | 动作 | 优先级 | 预期收益 | 成本 |
|---|---|---|---|---|
| A1 | 移除前端内置共享秘密和默认 Token | P0 | 避免凭据直接暴露 | 低 |
| A2 | 生产环境关闭网页任意 MCP command 注册 | P0 | 消除远程命令执行主路径 | 低~中 |
| A3 | 上传增加字节上限、类型校验和解析隔离 | P0/P1 | 降低 DoS 与解析器风险 | 中 |
| A4 | 质检未达数字引用硬阈值时默认拒交 | P0 | 保护“高可信”核心承诺 | 中 |
| A5 | UI 明示单用户自托管/预览版边界 | P1 | 管理用户预期 | 低 |
| A6 | 对齐 README、环境模板、测试数、预算和功能状态 | P1 | 消除交付口径冲突 | 低 |
| A7 | 增加根许可证、SECURITY、CHANGELOG | P1/P2 | 提升开源和企业可采用性 | 低 |

### 阶段 B：质量主线（3~6 周）

目标：从“LLM 写得像”升级为“证据可验证”。

| 编号 | 动作 | 优先级 | 预期收益 | 成本 |
|---|---|---|---|---|
| B1 | 建立结构化 Evidence/Claim/Citation 数据模型 | P0/P1 | 形成真正可审计证据链 | 中高 |
| B2 | SEC XBRL 财务事实结构化 | P1 | 提升财务数字准确性 | 中高 |
| B3 | 确定性数字-来源-期间-单位检查 | P1 | 显著降低无引用和错配 | 中 |
| B4 | 扩充并细标 100+ 条黄金集 | P1 | 建立可信评测基础 | 中高 |
| B5 | 当前版本全量统一重跑，不再合并跨版本指标 | P1 | 获得可比较基线 | 中 |
| B6 | 建立来源分级与冲突处理 | P1 | 提升来源可信度 | 中 |
| B7 | 增加提示注入与恶意文档红队集 | P1 | 降低 Agent 特有风险 | 中 |

建议阶段 B 的发布门槛：

- 关键财务数字证据支持率 100%；
- 普通数字紧邻引用率 ≥95%；
- 引用 URL 实际命中率 100%；
- 高风险模板默认 reject；
- 100 条分层任务成功率 ≥85%；
- 相同任务重复 3 次，核心事实一致率 ≥90%。

### 阶段 C：可靠性与运维（4~8 周）

目标：达到小团队内部生产可用。

- 任务、事件和状态跨进程持久化；
- 报告与问答分队列；
- 支持取消、重试、超时、幂等和死信；
- 索引版本化、无锁读取和原子切换；
- 标准 Prometheus/OpenTelemetry；
- 备份、恢复和迁移脚本；
- 7~30 天连续运行；
- 真实混合负载压测；
- 依赖/镜像扫描、SBOM、非 root 容器。

### 阶段 D：产品深化（6~12 周）

目标：验证真正的用户价值，而不是继续展示技术名词。

优先做：

1. 证据工作台：claim、原文、高亮、来源等级、冲突提示；
2. 公司/指标对比表；
3. 报告版本差异与人工批注；
4. 导出 Word/PDF/Excel 与引用附录；
5. 研究模板、数据范围和预计成本预览；
6. 用户反馈闭环：采纳率、返工原因、节省时间。

暂缓做：

- 与半导体主线无关的医学扩展；
- 为追热点而引入更多 Agent 框架；
- 没有明确查询价值的复杂 GraphRAG；
- 在质量门槛未达标前继续扩充生成模板。

### 阶段 E：企业化（有真实客户后）

只有出现真实团队客户和付费意愿后，再建设：

- OIDC/SSO、组织、RBAC；
- 租户数据隔离；
- KMS/Secrets Manager；
- 审计与合规导出；
- 配额、计费和成本中心；
- 高可用数据库、对象存储、灾备；
- SLA/SLO 与支持流程。

## 9. 最终结论

### 应继续坚持的方向

1. 半导体垂直研究，而不是通用 Agent；
2. 证据链、轨迹、评测和质检，而不是只追求文案流畅；
3. 工具治理、预算、降级和故障注入；
4. 公开记录失败与方法论限制；
5. 自研差异化集中在编排、证据治理和 Harness。

### 应立即停止或收缩的方向

1. 暂停无关领域横向扩张；
2. 不再用“Enterprise”掩盖单用户自托管边界；
3. 不把 LLM 质检 `passed` 当成事实正确证明；
4. 不把健康检查 QPS 当成研报系统吞吐；
5. 不把“代码已预留”描述为“生产能力已具备”；
6. 不在浏览器中保存服务器秘密；
7. 不允许网页注册任意可执行 MCP 命令。

### 项目经理视角的一句话评价

> 这个项目已经证明作者能把 Agent 从 Demo 做成完整工程；下一阶段真正决定项目含金量的，不是再增加一个热门功能，而是把“可信、可控、可运营”三个承诺做成可重复验收的硬指标。
