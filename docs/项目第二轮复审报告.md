## 1. 执行摘要

项目这次更新**确实取得了有价值的进展**，尤其集中在“事实质量与评测可信度”方面：

- 增加 URL grounding、来源分级和数字 claim 支持率；
- 增加确定性三门禁，不再只依赖 LLM 自评；
- Harness 开始检查黄金事实、过程性文本泄露和 URL 落地率；
- Harness 使用临时索引与临时报告目录，解决重复运行撞 Chroma ID 和 Harness 污染正式报告的问题；planner 相关测试也已隔离，但其他测试仍有残留污染路径；
- 修复了上一轮 TypeScript 的 `Array.at()` 兼容错误；
- Python 测试从 77 项增加至 87 项，本轮全绿（README 仍写 80，需继续对齐）；
- README 已明确历史指标不代表当前代码，文档诚实度提高。

这些更新说明整改方向是正确的，项目已从“主要靠提示词和同模型质检”向“提示词 + 确定性检查 + 可追溯证据”迈进。

但复审也发现两个重要事实：

1. **最危险的安全链路基本没有整改**：前端弱 Token、可伪造 Cookie、任意 MCP command、fetch SSRF、上传无限制仍然存在；
2. **新门禁目前仍是启发式聚合检查，不是 claim 与其具体引用的精确绑定**，可以被“报告中存在 URL、证据池中存在数字，但数字与该 URL 并不对应”的交叉错配绕过。

因此本轮建议将项目成熟度由上一轮 **3.0/5** 上调到约 **3.3/5**：

- 事实质量与评测工程有明显提升；
- 安全、并发、真实生产化和用户体验改善有限；
- 仍属于工程化原型/内部预览版，不适合公开部署。

## 3. 上一轮问题整改状态

### 3.1 已明确修复

#### A. Harness 重复运行与产物隔离

证据：

- `scripts/run_harness.py` 使用 `TemporaryDirectory` 构建隔离向量索引，并传入 `reset=True`；
- `agent/harness.py` 使用临时报告目录；
- `tests/test_planner.py` 将报告输出传到 `tmp_path`；
- 本轮实测 planner 测试前后正式报告目录数量不变。

评价：这是一个完整整改，不只是文档修改。

#### B. TypeScript 类型错误

`SessionDetail.tsx` 已改用 `events[events.length - 1]`，本轮 `tsc --noEmit` 通过。

#### C. 历史指标口径说明

README 和 `eval/metrics.md` 都明确声明 0.652/0.577 是跨版本历史基线，不代表当前版本。避免继续把旧指标包装为新版本能力。

#### D. Docker 忽略本地数据库和主要运行产物（部分修复）

`.dockerignore` 已排除 DB、向量库、模型、正式报告、`.env`、spikes、tests 等，较上一轮明显改善；但未排除 `agent/traces`，而 Dockerfile 会复制整个 `agent` 目录，因此本地轨迹仍可能进入镜像。

### 3.2 有实质改善，但仍不完整

#### A. 确定性质量门禁

当前加入：

- 数字级引用率；
- URL 落地率；
- claim 支持率；
- 来源等级统计；
- LLM 质检与确定性门禁叠加；
- reject/caveat 策略。

这比上一轮只依靠提示词和同模型 QA 强很多。

但存在以下问题：

1. 默认阈值偏低：数字引用率 30%、claim 支持率 50%，仍允许大量关键数字缺少支持；
2. 默认 `QA_POLICY=caveat`，门禁失败仍会交付正文；
3. 门禁结果只用于决定交付内容，没有持久化到 reports 表或 Session API；
4. 前端只读取 LLM verdict，不知道确定性门禁是否失败；
5. Session 会被标为 `done`，前端可能显示“全面通过”。

#### B. Harness 成功定义

Harness 已增加事实命中、checkpoint、过程泄露和 URL grounding，这是正确方向。

但当前事实匹配仍较宽松：

- `_fact_hit` 只要事实中的任意数字出现在报告就判命中；
- 实测报告只出现“2026 年”，即可命中“2026 年 7 月合并营收约 4,675.8 亿”的完整事实；
- 过程泄露关键词列表未覆盖 `<Thought>`、`<analysis>` 等常见形式；
- checkpoint 仍是 2-gram 启发式，不等于事实验证；
- success 没有纳入 number citation rate 和 claim support rate，只纳入 URL grounding。

因此新版 success 比旧版可靠，但仍不能等同于“事实正确率”。

#### C. 证据包

`agent/evidence.py` 已建立 URL、来源级别、数字 claim 与 evidence index，是非常好的结构化起点。

但当前 claim 支持判断为：同一论断中**任一数字**出现在任务证据池中，即整条论断 supported；没有验证：

- 报告数字后紧邻的那个 URL 是否包含该数字；
- 证据 span 是否支持整句话；
- 单位、币种、期间和公司是否匹配；
- 多个数字是否全部有证据。

本轮构造了交叉错配案例：报告中 `100 亿` 链接到 B、`999 亿` 链接到 A，而证据池中 A/B 正好反向包含数字。当前三项指标仍全部通过：number rate=1.0、URL grounding=1.0、claim support=1.0。

这说明门禁可以防“完全编造 URL”和“证据池完全没有该数字”，但还不能防“真实 URL 被错误绑定到错误数字”。

#### D. 评测可重复性

临时索引解决了 Chroma 重复 ID 冲突。但全量 Harness 仍有两个风险：

- 运行中途失败后缺少断点续跑，最后一次运行会覆盖 `results_latest.json`；
- `--ids` 或 `--limit` 的局部运行也会覆盖 latest，容易把局部样本误当全量基线。

建议输出带时间、代码版本和任务范围的独立结果文件，再显式 promote 为 latest。

## 4. 仍未整改的高风险问题

### 4.1 P0：弱共享 Token 仍写入前端和构建产物

`frontend/src/api.ts` 仍回退到 `dev-token-2026`，每次请求都发送 `X-API-Token`；`spikes/loadtest.py` 仍使用相同值。前端启动时自动登录，没有真正的凭据输入流程。

这意味着访问前端资源的人可以获得共享 Token。SSE 改为 Cookie 只解决 Token 不进 URL，没有解决 Token 已暴露给浏览器的问题。

### 4.2 P0：Cookie 默认密钥与认证绕过仍存在

`COOKIE_SECRET` 仍回落到 API Token，再回落到公开字符串 `dev-insecure-secret`；`require_auth` 的 cookie 分支没有要求 `auth_enabled()`。

当未配置 API Token 时，攻击者仍可使用公开默认值构造合法 Cookie。

Cookie 仍缺少：

- `Secure`；
- 服务端会话与吊销；
- CSRF Token；
- 独立强随机密钥强制校验。

### 4.3 P0：MCP 任意命令执行仍存在

网页/API 仍可提交任意 `command + args` 注册 stdio MCP Server；发现时还会使用 `os.environ.copy()` 将完整宿主环境传给子进程。

这与弱 Token 组合后仍形成完整高危链路：

> 获取浏览器内置 Token → 注册任意命令 → 服务端子进程执行 → 读取宿主环境密钥。

### 4.4 P0/P1：fetch SSRF 未处理

`fetch_server.py` 仍允许任意 URL 和自动重定向，没有阻止：

- localhost/127.0.0.1；
- 私有网段；
- `169.254.169.254` 云元数据；
- DNS rebinding；
- 重定向到内网地址；
- 非预期 Content-Type 和超大响应体。

### 4.5 P1：上传仍无限制且同步重建

上传接口仍先 `await file.read()` 全量读入内存，无文件字节上限、MIME/魔数校验和解析隔离；上传后同步执行全量 reindex。

### 4.6 P1：提示注入仍未形成系统防线

新 Evidence 门禁属于输出侧检查，不能防止恶意网页/文档诱导 Agent：

- 调用敏感工具；
- 泄露上下文；
- 改写研究目标；
- 进行 SSRF 或 MCP 调用。

尚未发现结构化内容隔离、污点标记、高风险工具人工确认或提示注入红队测试。

## 5. 工程与架构剩余问题

### 5.1 async 阻塞和全局串行未修复

`ask_question` 仍在 async 路由中直接运行同步 LLM 流程；上传仍同步 reindex。

`ReportService` 继续使用同一 `RLock` 包裹：

- 报告生成；
- 问答；
- 重建索引。

因此报告生成期间问答和其他生成任务仍接近串行，线程池 max_workers=2 并没有转化为真实吞吐。

### 5.2 RQ/SSE 多进程链路仍未闭环

事件总线仍是进程内 `queue.Queue`；RQ worker 与 API 分进程时无法共享 SSE 事件。Compose 中 Redis/worker 仍只是注释预留。

### 5.3 SSE 用户体验未改善

前端 `EventSource` 的 error 处理仍直接关闭连接，没有自动重连、退避、Last-Event-ID 或状态补偿。长任务中一次网络波动仍可能造成界面假死。

后端也只推送少量 phase 事件，没有真正流式展示工具调用或逐节状态。

### 5.4 前端仍存在误导性状态

- 继续显示 `Enterprise v0.3.0`；
- “SEC EDGAR + arXiv 知识引擎就绪”为静态常绿状态；
- 质检 passed 时显示“全面通过（100% 来源核实）”；
- 描述称“所有核心数据均完成双向闭环核实”。

这些文案没有读取确定性门禁结果，且当前门禁也不能证明 100% 来源核实。

这是本轮新增后的一个明显前后端契约缺陷：后端门禁变强了，前端却仍只展示旧 verdict。

### 5.5 门禁计算位置过晚且状态不一致

Evidence/claim 指标在报告写入文件之后计算；服务层再计算 deterministic gate。即使 `QA_POLICY=reject`：

- 原始报告文件已经写入 `reports/output`；
- 数据库正文可以拒交为空，但文件仍保存完整内容；
- Session 状态仍设为 done；
- 保存的 verdict 仍是 LLM verdict，没有保存 gate；
- 前端可能把 LLM passed 显示为全面通过。

建议建立统一 `delivery_status`：passed / caveat / rejected，并将 gate 结构持久化。

### 5.6 外部 API 治理仍不统一

README 仍声称 PubMed 统一超时、退避和故障注入，但 PubMed 实现仍直接调用两次 `requests.get`，没有复用 `external_get`。

### 5.7 CI 与供应链整改有限

- CI 仍没有独立 `tsc --noEmit`，虽然当前本地通过，但未来仍可能漏检；
- 仍使用 `npm install` 而不是 `npm ci`；
- 无 Python/容器漏洞扫描、SBOM、许可证检查；
- 根目录仍未发现项目自身 LICENSE、SECURITY、CHANGELOG、pyproject.toml；
- 容器仍以 root 运行，基础镜像未锁 digest。

`.dockerignore` 虽改善，但 `agent/traces` 没有明确排除；`COPY agent ./agent` 可能把本地轨迹一起复制进镜像。建议加入 `agent/traces`。

### 5.8 测试产物隔离仍有一条残留路径

`tests/test_enterprise.py` 的 fallback 回归测试虽然 monkeypatch 了 `settings.REPORT_DIR`，但 `ReportPipeline.generate()` 实际使用显式 `output_dir` 参数或硬编码默认 `ROOT/reports/output`，并不读取 `settings.REPORT_DIR`。该测试调用 `pipe.generate("测试选题")` 时仍可能写正式报告目录。

本轮单独验证 planner 测试没有污染，但全套测试运行已实际产生 `report_weekly_20260820_150914.md` 和 `report_weekly_20260820_150952.md` 两个 24 字节空壳，确认该残留路径仍会污染正式目录。建议所有调用 `generate()` 的测试显式传 `output_dir=tmp_path/...`，并在全套测试外层做目录前后差异断言。本轮遵守禁止修改代码/产物的要求，没有代为删除这两个文件。

### 5.9 其他仍存问题

- 限流路径匹配逻辑未修，X-Forwarded-For 可伪造，bucket key 不回收；
- `recover_stale()` 仍在应用构造/导入阶段执行；
- metrics 仍为进程内计数器；
- fallback 仍使用独立完整预算；
- Google News 代理仍硬编码到本机 127.0.0.1:10808；
- 数据加载固定 limit=1000；
- 记忆新增了 bigram/实体去重，这是进步；但同一实体即被视为同主题重复，可能把“关注台积电先进制程”和“关注台积电财务表现”等不同偏好合并；更新 SQLite 文本时也没有同步 upsert 已存在的向量文档，向量内容可能继续保持旧版本；
- PubMed 实时请求仍绕过统一治理；
- `list_sessions(limit)` 未设置上界；
- CodeAgent 仍是进程内软沙箱，而非 OS 级隔离。

## 6. 新增实现中需要重点修正的问题

### 6.1 Claim 支持率存在“任一数字支持整句”的逻辑漏洞

`claim_support_rate()` 当前使用：

```text
if any(n in index for n in c["numbers"]): supported += 1
```

一句话中有多个数字时，只要任意一个数字在任意证据中出现，整条 claim 即通过。应改为：

- 关键数字全部命中；
- 每个数字绑定其紧邻引用 URL；
- 该 URL 对应 span 中出现相同标准化数字；
- 同时校验单位、币种、期间、主体。

### 6.2 URL grounding 只证明 URL 出现过，不证明引用关系正确

任务中某 URL 被任何工具返回过，就可用于报告任何论断。需要从“报告 URL ∈ 工具 URL 池”升级为：

> claim 中的数字/事实 → 紧邻 URL → 同 URL 的证据 span → 语义支持。

### 6.3 来源分级存在分类争议

`trendforce.com`、`macrotrends.net`、`companiesmarketcap.com` 被列为“官方/监管/公司披露”，这会抬高 official_ratio。它们更适合行业数据服务或聚合数据，而非官方披露。

此外“官方/学术来源占比”将官方和学术混为一个比例，不适用于要求财务数字必须来自 SEC/公司公告的场景。

建议至少区分：监管/公司官方、学术原文、行业数据服务、主流媒体、聚合/未知、用户上传。

### 6.4 空证据默认满分可能掩盖无证据报告

当前：

- 报告没有 URL 时 URL grounding rate=1.0；
- 报告没有 meaningful numeric claim 时 claim support rate=1.0；
- 报告没有 URL 时 official_ratio=1.0。

这些值作为技术上的 vacuous truth 可以理解，但用于质量评分时会使“无数字、无引用、无证据”的报告看起来全部满分。应同时记录 coverage/total，并对需要证据的报告类型设最小引用数和最小 claim 数。

### 6.5 数字引用率默认阈值与产品承诺不一致

项目要求“每个精确数字紧跟来源”，但门禁阈值只有 0.3。若这是开发期宽松阈值，应在 UI/README 明确；正式研投模板应接近 1.0。

### 6.6 Chroma 非 reset 路径可能形成静默向量错位

当前文档和 Harness 已通过临时目录解决重复 ID 问题，但应用启动和 `scripts/evaluate.py` 的真实索引路径仍可能以 `reset=False` 调用 `collection.add()`。在当前 Chroma 版本中，重复 ID 可能被忽略而不是抛出明显异常；同时 doc_id 使用位置式 `art{i}-c{j}`。

当文章顺序或内容发生变化时，BM25/文档字典可能使用新文本，而 Chroma 中同 ID 的 embedding 仍是旧文本，形成难以察觉的混合检索错位。建议 doc_id 基于稳定文章主键+内容哈希，并使用 upsert 或索引版本原子重建。

## 7. 建议优先级

### P0：公开部署前必须完成

1. 删除前端硬编码 Token，改为真实登录/首次初始化流程；立即轮换现有凭据；
2. COOKIE_SECRET 独立强随机且必填；Cookie 校验必须要求 auth enabled；设置 Secure；
3. 关闭网页任意 MCP command，改后端白名单；MCP 子进程使用最小环境；
4. fetch 增加协议、IP、DNS、重定向和响应体限制；
5. 上传增加字节、类型、页数、解析超时和隔离；
6. 统一 gate 与 verdict，避免 LLM passed 但确定性 gate failed 仍显示全面通过。

### P1：下一轮质量整改

1. 将 claim 与其紧邻 URL 和对应 evidence span 精确绑定；
2. 关键数字要求 all-match，而不是 any-match；
3. 校验单位、币种、期间和主体；
4. 修复 Harness 年份误命中和过程泄露词表；局部 `--ids/--limit` 运行不得直接覆盖全量 latest；
5. success 纳入 deterministic gate 的全部指标；
6. 全量运行当前版本 24 条 Harness，并保留独立版本化结果；
7. 默认研投 `reject`，数字引用率阈值提高到 95%~100%。

### P2：工程生产化

1. 拆分锁和任务池，问答/生成/reindex 分离；
2. 完成真正的跨进程任务事件通道，或移除 RQ 预留宣称；
3. SSE 自动重连、状态恢复、任务取消；
4. CI 增加 typecheck、lint、依赖和镜像扫描；
5. 补许可证、安全策略、变更日志和标准打包；
6. 前端状态从真实 health/gate 获取，移除“100% 核实”等绝对文案。

## 8. 复审结论

### 本次更新做得最好的三件事
