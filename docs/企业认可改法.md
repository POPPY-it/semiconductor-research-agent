# 半导体研究 Agent：企业认可的改法建议

> 文档目的：把审阅后的改法建议固化，方便换人/换模型继续对齐。
> 审阅范围：`D:\qwen3.6\semiconductor-agent`，只评价不改代码后的结论。
> 面向：2027 届硕士、主投 Agent（合合 / 讯飞 / 百度 / 思必驰 / 同程）。
> 原则：企业认的不是「功能更多」，而是问题清楚、Agent 闭环可测、数字可复现、叙事不虚。
> 改法：收窄、加深、可验收，不是再堆医学综述、再接两个 MCP。

---

## 0. 给接手人的一页纸

- **现状**：能跑通的全栈研究助手（采集 + RAG + 双 Agent 循环 + FastAPI/SSE + MCP + 预算熔断 + 质检策略），但定位更像「带 Agent 外壳的 RAG 研报流水线」。
- **不要再加**：新领域、第三个 MCP、Celery/JWT/多租户、真 GraphRAG、重写前端。
- **应该改**：收窄成半导体主线、显式规划、轨迹落盘、局部修订、工具 schema、20 条可复现评测。
- **建议先做 P0**：改 README/PLAN 口径 + 轨迹 JSONL + 修订降本。再做 P1：20 条任务集 + `harness.py` + 工具治理 + 按节规划。
- **简历口径**：按「产品化开源内核 + 检索/质检/治理 + 可评测 Harness」讲，不要按「自研多智能体框架 / GraphRAG / Mem0 / SFT」讲。

---

## 1. 先定死一句话

现在对外有三套说法：半导体研报、多领域研究助手、企业级 Agent。面试官会拆。

建议定成这一句，然后所有 README / PLAN / 简历 / Demo 都跟它走：

> **半导体研究 Agent：给定选题，用工具检索公开财报与论文，按规划写出带引用的报告，并用可复现的评测集衡量「引用是否站得住、工具有没有乱调」。**

医学、日常问答、网页端随便加 MCP，都降成「扩展点」，不再当主叙事。半导体主线要收回来，三领域摊薄是当前最大减分项。

---

## 2. 企业真正看的 4 件事

合合 / 讯飞 / 百度 / 思必驰问 Agent，通常就这四块：

| 他们要的 | 你现在 | 应该改成 |
|---|---|---|
| **Harness**（任务怎么跑、失败怎么收） | 固定「写稿→质检→整篇重写」 | 有规划、有轨迹、有预算、有可回放日志 |
| **工具调用** | 模型自己写代码调工具，成功失败靠运气 | 工具有 schema、校验、重试、错误回传 |
| **评测** | 评的是 RAG Recall，不是 Agent | 20～50 条任务：成功率 / 步数 / 无引用数字率 / 成本 |
| **诚实分层** | PLAN 写三 Agent + Celery + JWT | 文档和代码一致：复用内核，自研编排/检索/治理 |

SFT/DPO 没有数据就不要硬做。有评测集和轨迹日志，比假微调更像「做过 Agent」。

---

## 3. 不要改的（再加就是减分）

- 不要再加 PubMed / 医学综述 / 新领域模板
- 不要再加第三个 MCP Server、网页端「任意注册 command」
- 不要上 Celery / JWT / 多租户，除非真要上线给别人用
- 不要把 Graph 改造成「真 GraphRAG」，词典共现图够用，改名即可
- 不要重写前端；工作台能演示 SSE 就行

砍比加更像企业项目。

## 4. 审阅要点（改之前必须知道的现状）

### 4.1 真正落地的部分

主链路：

`采集适配器 → SQLite → 分块/混合检索/重排 → CodeAgent 写稿 → 质检 JSON → 修订 ≤2 轮 → 质检策略落盘 → FastAPI + SSE`

值得保留并写进简历的硬点：

1. **检索有实验依据**：加权 RRF（BM25 0.7 / 向量 0.3）来自 W2 实测；`char_bigram` 替代 jieba 是环境约束下的工程选择。
2. **质检有产品策略**：`caveat` 打横幅、`reject` 拒交。W4 日志已写：质检是可验证性门槛，不是真伪判定；修订第二轮累计约 52 万 input。
3. **服务层不是空壳**：Cookie 鉴权、限流、中断会话恢复、任务重试、索引与生成互斥、Prometheus 文本指标；`tests/test_enterprise.py` 覆盖了其中大部分。
4. **评测有方法论反思**：真实语料 Recall@5 = 0.127，已归因到粗粒度关键词标注；faithfulness 偏低归因到 judge 上下文不是真实引用。见 `docs/p3-eval-report.md`。
5. **MCP 是真接上的**：`github` / `fetch` 两个 stdio server，编排里挂成 `mcp_call`。

### 4.2 和 PLAN / README 对不上的地方

| 文档怎么写 | 代码实际是 |
|---|---|
| 研究 / 数据 / 质检三 Agent + 状态机 | 只有 Researcher + QA；「数据 Agent」是工具，不是独立角色 |
| Celery + Redis + JWT | 默认 `ThreadPoolQueue`；鉴权是单 token Cookie，不是用户隔离 JWT |
| SEMI / SIA / 集微网 | 实际是 SEC + arXiv + PubMed + 新浪/IT之家/Google News RSS |
| 半导体行业研报产品 | 已扩成行业 / 学术 / 医学三领域，半导体主线被模糊 |
| W7 上线 + 压测 + 连续运行 1 周 | README 仍未勾；Docker 有，压测/HTTPS/连续产出未见硬证据 |
| PLAN 里 M1–M7 复选框仍空 | README 写 W1–W6 已完成 |

PLAN 还停在「施工图」，README 已写成「产品说明书」。面试前先统一口径。

### 4.3 Agent 层现状

`ReportPipeline.generate()` 本质是：

1. 长期记忆检索（失败吞掉）
2. Researcher `CodeAgent` 写一稿（`max_steps=12`）
3. QA `CodeAgent` 吐 `{"passed","issues"}`（解析失败重试 1 次）
4. 不过就带着 issues 再跑 Researcher（`reset=False`，最多 2 轮）

这是**固定流水线**，不是可学习的规划器。没有任务分解图、没有中间产物 schema、没有按节修订（W4 自己也写了「应只回填问题段落」但没做）。

工具面够用：知识库、SEC、arXiv、Semantic Scholar、PubMed、图谱、出图、MCP。但轨迹没有结构化落盘，也没有 tool-use 成功率 / 步数 / 幻觉率的 Agent 评测。`agent/eval.py` 评的是 **RAG**，不是 Agent。

### 4.4 名实不完全相符的模块

- **GraphRAG-lite**：词典匹配 + 共现边 + 度中心性。应改名为「实体共现图」。没有 LLM NER、社区摘要、沿图生成答案。
- **Mem0-style 记忆**：抽取 → SQLite → 向量召回，骨架对。缺更新、去重、冲突合并。关键词回退用「字符集合重叠」，中文几乎总能糊上。单用户 `default`。
- **MCP**：每次 `discover` / `_call_tool` 都 `asyncio.run` 拉起新 stdio 进程。Agent 侧是一个调度器 `mcp_call(tool_name, arguments)`，模型要先记住工具名再拼 JSON。网页端还能注册任意 `command`。
- **安全**：CodeAgent 会跑模型生成的代码；MCP 可注册任意命令；鉴权是共享 token。秋招 demo 够用，不要说「企业级多租户安全」。

### 4.5 工程细节（面试可能被点名）

- `loader.py` 每次 `limit=1000` 全量建索引 + 构图；`reset=True` 才清 Chroma。上传文档后全量重建。
- 问答展示用 `search_hybrid`，写稿工具用 `search_reranked`，前后检索不一致。
- `test_report_templates_cover_types` 只断言了 daily/weekly/deep，`survey` / `medical_survey` 没测。
- 医学综述有免责声明；但 PubMed 工具 + PICO 模板 ≠ 可靠医学 Agent。
- `.env` 在仓库目录里（已 gitignore）。确认从未提交过 key。
- `smolagents-src/` 作精读参考可以，面试要能指出改的是编排/工具/治理，不是 fork 内核。

### 4.6 审阅时发现的代码风险（改代码时可一并核对）

1. **fallback 切换可能没切到新 Agent**  
   `switch_to_fallback()` 用 `nonlocal` 重建了 `researcher` / `qa`，但 `guarded_run` 里接着调的仍是参数 `agent`（旧实例）。请在改编排时核对并修复。
2. **记忆向量召回可能拿错行**  
   `MemoryStore.search` 把 Chroma 的 `doc_id` 当成 `all_texts` 的下标；`all_texts` 是 `ORDER BY id DESC LIMIT 200`。id 不连续时会错位。
3. **`_extract_json` 贪心正则**  
   `re.search(r"\{.*\}", text, flags=re.S)` 遇到多个花括号容易吸错。

## 5. 按优先级改：三期，大约 2～3 周

### P0（本周，面试叙事立刻变硬）

#### P0-1. 统一口径，删虚词

- README / PLAN 对齐：两个角色（研究 + 质检），不是三 Agent 状态机
- 队列写成 ThreadPool（RQ 是预留），鉴权写成共享 Cookie Token
- 数据源写成实际的 6 个，不要 SEMI/SIA/集微网
- GraphRAG / Mem0 改名为「实体共现图」「跨会话偏好记忆」
- PLAN 里空复选框要么勾上并写证据，要么删掉

**验收**：陌生人只看 README，说不出和代码相反的话。

#### P0-2. 轨迹落盘（Harness 的最小闭环）

每次 `generate` / `answer_question` 写一份 JSONL，至少包含：

- `task_id`、选题、报告类型
- 每步：角色、工具名、参数摘要、返回摘要、耗时、是否报错
- 质检 `verdict`、修订轮数
- token/字符预算、主备模型、总耗时
- 报告里抽出的「数字 + 是否带 URL」

没有这份日志，后面所有评测都是空话。企业看的是「你能不能回放一次失败」。

#### P0-3. 修订降本（W4 已写、但没做）

质检不过时，只重写被点名的段落，不要整篇重跑。`reset=False` 可以留，但任务要从「重新输出完整报告」改成「只替换第 N 节」。

**验收**：同一选题，修订轮的 input 字符明显低于现在「第二轮 52 万」那个量级，并写进报告。

---

### P1（下周，Agent 岗能对上 JD）

#### P1-1. 最小评测集（20 条就够，不要 200）

每条任务固定：

- 选题（例如「台积电最近一个 10-Q 的营收与指引」）
- 必须用到的工具（`query_filings` / `search_knowledge`）
- 禁止出现的幻觉模式（无 URL 的精确数字）
- 参考要点（3～5 条可核对事实，精确到文档/段落，不要再用关键词当 gold）

指标只留企业听得懂的 4 个：

1. **任务成功率**：质检通过，或 caveat 但无「无来源数字」
2. **无引用数字率**：正文里金额/百分比有多少没带链接
3. **平均工具步数 / 失败重试次数**
4. **单任务成本**：字符或估算 token、墙钟时间

RAG 的 Recall/MRR 降为附录。黄金集改成精确 `doc_id`，这是 `docs/p3-eval-report.md` 里已经承认的坑。

#### P1-2. 工具层收成「可治理」

现在工具散落在 `_make_tools()` 里，MCP 还是一个 `mcp_call(name, json)`。企业更认：

- 每个工具一份 JSON schema（必填字段、范围、超时）
- 参数校验失败要回给模型「哪错了」，不要抛到编排器外面
- 外部 API（arXiv / S2 / PubMed）统一：超时、429 退避、降级文案
- MCP：只保留 github + fetch；每个 MCP 工具映射成独立 Tool，不要让模型先背工具名再拼 JSON
- 写稿检索和问答检索统一走同一套（现在一个 `reranked`、一个 `hybrid`）

**验收**：人为把 arXiv 超时，任务仍能用知识库+SEC 出一版带 caveat 的报告，而不是整单炸掉。

#### P1-3. 规划显式化（仍不必自研框架）

在 Researcher 跑之前，先产出一份短规划（可用一次便宜的 LLM 调用，或规则模板）：

```text
大纲：4 节
每节检索：哪些工具、什么 query
数字必须来自：SEC / 知识库
禁止：无来源精确数字
```

然后按节写，质检按节判。这就是 JD 里的「规划 + Harness」，比再套一个 Multi-Agent 框架更像企业做法。

---

### P2（有余力再做，用来挡深挖）

#### P2-1. 记忆做成「有用」或删掉展示位

现在缺去重、更新、冲突合并，关键词回退几乎总能糊中。要么：同一事实只保留最新一条 + 简单去重；要么 Demo 里不讲记忆，避免被追问 Mem0。

#### P2-2. 图谱改名并加 1 个可演示问题

例如「台积电和 HBM 在语料里共同出现在哪些文档」。能回答「跨文档关联」就够了。不要上社区摘要。

#### P2-3. 一条可复现的压测/成本数字

不必真上云。本地 20 条评测集跑一遍，交出：P50/P95 时延、失败率、单篇估算成本。PLAN 里「2 小时→15 分钟」没有计时就删掉。

#### P2-4. Demo 脚本固定 3 分钟

选题 → SSE 看到工具调用 → 打开带引用的报告 → 打开一条轨迹 JSON → 打开评测表。比再做一页前端有用。

## 6. 建议的目标结构

```text
semiconductor-agent/
  agent/
    planner.py          # 显式大纲，按节分配工具
    tools/              # 每个工具独立模块 + schema
    orchestrator.py     # 按节写 + 按节质检 + 局部修订
    harness.py          # 跑评测集、写 JSONL、出汇总表
    traces/             # 每次运行的轨迹
  eval/
    tasks.json          # 20 条半导体任务（精确标注）
    metrics.md          # 最近一次分数（提交进 git）
  docs/
    README 只讲这一条主线
    企业认可改法.md   # 本文档
```

现有 RAG、采集、FastAPI、前端都可以留，但它们是底座，不是卖点。

## 7. 简历口径

### 改完 P0+P1 后可以写

> 基于 smolagents CodeAgent 做半导体研究 Agent。输入选题后先规划大纲，再按节调用 SEC/知识库/论文工具写作，质检按「数字必须带出处」卡关，失败只修订问题段落。自建 20 条任务的 Harness：记录每步工具轨迹，统计成功率、无引用数字率、平均步数和成本。检索侧用加权 RRF + reranker，并复盘过粗粒度标注会压低 Recall。

这句话里每一段都能指到文件。

### 不要写

- 自研多智能体框架 / GraphRAG / Mem0
- 企业级多租户安全
- 研报 2 小时降到 15 分钟（除非有可复现计时和线上连续产出）
- SFT/DPO（除非真做了）

## 8. 和目标公司怎么对

| 公司 | 改完后主攻哪句 |
|---|---|
| **合合** | Harness + 规划 + 工具 schema + 评测集，RAG/质检当证据 |

## 10. 建议的下一步起点（让接手人选）

优先级从高到低：

1. **先改文档口径**：README + PLAN 删虚词、对齐实际架构（不动业务逻辑）
2. **再做轨迹落盘**：`generate` / `answer_question` 写 JSONL
3. **再做 `harness.py` + 20 条任务集**
4. **再改编排**：局部修订 + 显式规划
5. **最后收工具层**：schema / 降级 / MCP 拆分

不要从前端、新数据源、医学领域、真 GraphRAG 开始。

## 11. 一句话

**少做产品功能，多做：收窄领域、显式规划、轨迹、局部修订、20 条可复现评测。**  
企业要的是你能证明 Agent「什么时候成、什么时候败、败了怎么收」，不是再多一个数据源。
