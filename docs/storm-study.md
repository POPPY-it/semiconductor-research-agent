# STORM 技术精读笔记（对标学习：为什么"长研报"质量高）

> 对象：Stanford STORM（"Assisting in the Writing of a Long Report"，NAACL 2024，
> github.com/stanford-oval/storm）。OpenAI/Gemini/千问 Deep Research 的工作流与之同源
> （规划 → 并行检索 → 大纲 → 分节写作 → 引用）。
> 本文 = 精读笔记 + 本项目落地对照（2026-08 实施版）。

## 1. STORM 的四个核心机制

### 1.1 多视角提问（Question Asking）
- 先让 LLM 模拟**不同读者视角**（行业分析师、投资者、技术研究者…）对选题提问；
- 这些"视角问题"比直接用主题做检索词**覆盖面更广**（同一主题，不同视角关心的点不同）；
- 视角问题被转成检索查询，先收集一轮"信息地图"，为大纲提供依据。

### 1.2 大纲生成（Outline Creation，coarse-to-fine）
- 基于初步收集的信息生成**粗大纲**（章节标题），再逐节细化；
- 大纲不是拍脑袋，而是"检索之后"的大纲——每节的标题都对应已收集到的资料。

### 1.3 分节信息收集（Parallel Information Collection）
- 对大纲的每一节，**独立、并行**检索并收集资料，存入"每节资料库"；
- 关键：**检索与写作分离**——检索阶段的资料以结构化条目存储（含来源），写作阶段不再重新检索；
- 每节资料独立 → 写作时**每节只带自己的资料上下文**，避免整篇长文的上下文爆炸（我们 24 条评测里 survey 任务 token 烧得快，根因就是没有这个分离）。

### 1.4 分节写作 + 引用强制（Section Writing with Citation）
- 每节独立写作，prompt 强制**每个论断带引用**（引用编号指向该节资料库条目）；
- 写作过程中不检索（防止写作-检索互相干扰 + 控制成本）；
- 引用密度是**写出来的**，不是事后补的——这是"段落级可验证"的来源。

### 1.5 反思（Reflection）
- 写完后让模型检查"引用是否支持论断"，标记存疑处。

## 2. 为什么这套机制产出高质量长文

| 设计 | 解决的问题 |
|---|---|
| 检索与写作分离 | 长文上下文爆炸（token 成本）；写作被检索噪音干扰 |
| 每节独立上下文 | 每节聚焦、深度够，成本线性而非平方 |
| 多视角提问 | 覆盖盲区，报告"视角完整"（不只顺着一个角度写） |
| 写作时强制引用 | 引用可验证 = 幻觉可拦截；段落级可回放 |
| 大纲驱动 | 结构稳定，不会写着写着跑偏 |

## 3. 与本项目对照（落地设计）

| STORM 机制 | 我们落地（2026-08 实施） | 状态 |
|---|---|---|
| 多视角提问 + 大纲 | `agent/planner.py` 新增 LLM 版：一次调用生成 JSON 大纲（sections: title/focus/search_queries），失败回落规则模板 | ✅ 已实施 |
| 大纲驱动写作 | 大纲注入 Researcher 任务，指令要求按规划逐节写 | ✅ |
| 分节写作 | Researcher 指令："每节先检索再写，写完一节再下一节"（CodeAgent 内实现） | ✅ |
| 引用强制 | 写作纪律："**每个段落结尾必须带 [来源](url)**" | ✅ |
| 引用可验证 | harness 新增**引用密度指标**（带链接段落占比）+ QA 按节查无来源段落 | ✅ |
| 每节独立上下文 | 部分落地：CodeAgent 的 reset=False 保留全历史（成本仍高），**未来可做"分节独立 run 再拼接"** | ⏳ 待做 |

## 4. 面试话术（对标 Deep Research 类产品）

> "体验过千问深度研究：差距在模型与数据两层（万亿参数旗舰 vs 小模型、实时行情+百万财报 vs 静态语料）。
> 我能做的是编排层的论文级落地：多视角大纲规划（LLM 生成章节+检索词）、分节写作 + 段落级引用强制、
> 引用密度作为 harness 指标评测。这层是可验证的工程能力，与模型大小无关。"
